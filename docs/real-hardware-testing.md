# Phase 13 — Real Hardware Testing

This phase is inherently physical: it happens on your actual dual-boot
machine, not in QEMU. This doc is the runbook; `diagnostic/install/`
has the scripts it walks through. **Do not skip steps or reorder them
— the ordering is the safety mechanism.**

## Before you touch the real machine

1. **Full disk image backup**, not just a Windows restore point. If
   something outside this repo's control goes wrong (bad USB firmware,
   a flaky ESP write, whatever), you want a real way back. `dd` the
   whole disk to external storage, or use your normal backup tool —
   this is standard "about to touch the bootloader" hygiene independent
   of PLDDS.
2. Know your BIOS/UEFI boot-menu key (F12/F10/Esc/F2 — varies by OEM)
   and confirm you can reach the UEFI boot menu / firmware setup before
   doing anything else. You'll need this if GRUB itself ever fails to
   show a menu.
3. Have a **second machine or phone** free to read this doc / search
   for help if the test machine is mid-recovery.

## Step-by-step

### 1. Build the artifacts

```bash
cd diagnostic
./build/build-kernel.sh        # produces build/output/vmlinuz
./build/build-initramfs.sh     # produces build/output/initramfs.cpio.gz
```

Both scripts fail loudly with a clear message if a dependency is
missing — don't proceed past a red error here.

### 2. Test in QEMU first — again

Even if you've run the Phase 10 QEMU harness before, run it once more
against this exact build:

```bash
scripts/run-qemu.sh
```

Confirm: boots, agent runs, uploads a report, server ACKs, reboots.
QEMU is not the real machine, but a build that fails here has no
business touching real hardware.

### 3. Pre-flight check on the real machine

```bash
cd diagnostic/install
sudo ./preflight-check.sh
```

This is read-only — it changes nothing, only reports. Fix every
`FAIL` line before proceeding. `WARN` lines (e.g. Secure Boot enabled)
are judgment calls — read what they say.

### 4. Build and verify recovery media

```bash
sudo ./make-recovery-usb.sh /dev/sdX   # your spare USB drive, will be erased
```

Then **actually test it boots** before proceeding — either:
- in QEMU: `qemu-system-x86_64 -bios /usr/share/OVMF/OVMF_CODE.fd -drive if=none,id=usb,file=/dev/sdX,format=raw -device usb-storage,drive=usb`, or
- on a spare machine's UEFI boot menu, confirming it reaches a Windows
  Boot Manager screen (or your recovery machine's own OS, if you're
  testing against a non-Windows spare).

Do not proceed to step 5 until this media has been verified to boot.
This is the whole safety net for everything after this point.

### 5. Install

```bash
sudo ./install.sh
```

Walks through: backup current GRUB config → copy `vmlinuz` +
`initramfs.cpio.gz` to `${ESP}/pldds/` → generate the GRUB menuentries
with this machine's real partition UUIDs → append them via
`/etc/grub.d/41_pldds` (Windows' own entry, generated by the distro's
existing `grub.d` scripts, is never edited) → run `update-grub` /
`grub-mkconfig` → **verify** the regenerated `grub.cfg` still defaults
to `windows` and still has a Windows Boot Manager entry, automatically
rolling back if not.

If it prints `SUCCESS`, continue. If it prints an error and rolls
back automatically, you're back to pre-install state — read the error,
fix the underlying issue, and re-run from step 3.

### 6. First reboot — manual verification only

Reboot. At the GRUB menu you should see three entries:
`Windows Boot Manager`, `PLDDS Diagnostic Linux`,
`PLDDS Diagnostic Linux (safe mode)`.

- **First, let it time out / do nothing** — confirm it boots Windows
  by default (the whole point of the safety invariant).
- **Reboot again, this time manually select** `PLDDS Diagnostic Linux
  (safe mode)` from the menu. Safe mode skips anything beyond
  read-only collectors — lowest-risk first real-hardware boot.
- Confirm: kernel boots, agent runs, collectors produce sane-looking
  output for *your actual hardware* (not QEMU's virtual devices —
  this is the first time GPU/USB/network/sensors collectors see real
  silicon), and either uploads successfully or fails gracefully and
  still hands off to Windows per the boot-flow doc.
- **Only after that succeeds**, manually select the regular
  `PLDDS Diagnostic Linux` entry and confirm the same, then test the
  actual one-shot flow: from a normal Windows or diagnostic boot,
  trigger whatever schedules `grub-reboot diagnostic`
  (see `docs/boot-flow.md`) and confirm the *next* boot goes to
  diagnostic once, and the boot *after that* reverts to Windows on its
  own with no PLDDS code needing to run.

### 7. Soak test

Run several real boot cycles over a day or two — dual-boot machines
that work once and then don't (thermal issues on cold boot, a USB
device that behaves differently after suspend, etc.) are exactly what
QEMU can't catch. Log anything odd, even if it self-recovered.

### 8. If you need to remove it

```bash
cd diagnostic/install
sudo ./uninstall.sh
```

Restores the original `grub.cfg`/`grubenv`/`40_custom` from the backup
`install.sh` took, removes `/etc/grub.d/41_pldds` and
`${ESP}/pldds/`, regenerates via the distro's own tooling, and
verifies a Windows entry is present in the result.

## What "done" looks like for this phase

- [ ] Preflight checks pass on the real machine
- [ ] Recovery USB built AND independently verified to boot
- [ ] `install.sh` completes with `SUCCESS` and its own verification
- [ ] Windows boots by default with zero interaction, confirmed
- [ ] Windows boots correctly when manually selected, confirmed
- [ ] `PLDDS Diagnostic Linux (safe mode)` boots and runs collectors on
      real hardware, confirmed
- [ ] `PLDDS Diagnostic Linux` (normal mode) boots, uploads a report,
      server ACKs it, confirmed against the real backend (not
      `localhost`/QEMU's `10.0.2.2`)
- [ ] One-shot `grub-reboot diagnostic` → diagnostic boot → next boot
      reverts to Windows automatically, confirmed
- [ ] Soak test run across multiple real boot cycles with no surprises
- [ ] `uninstall.sh` tested at least once and confirmed to fully
      restore the pre-install state

Only once every box above is checked should this be considered
something other people's machines could run — this repo has, up to
this point, only ever been proven in QEMU.
